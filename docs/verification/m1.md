## Operational limits and pending owner decisions

Review [the runbook](../runbooks/m1-tenancy-provisioning.md) before accepting this implementation.

1. M1 supports one trusted operations machine with a private durable local lock directory. It deliberately blocks cross-host automatic takeover. Do not use shared/network lock storage, copy host identity, or delete active lock files. Distributed maintenance failover is not claimed.
2. A crash after database creation but before its immutable identity/installation marker is persisted leaves an unidentified database. Retry fails closed; approved provenance investigation/reconciliation is required. It never automatically drops, adopts or writes a new identity into that database.
3. Dedicated SQL-authenticated maintenance identities and injected runtime secrets are the implemented adapter. Production secret distribution, TLS certificate validation, SQL account provisioning policy and restricted operations-host access remain deployment responsibilities. CI uses disposable SQL Developer fixtures only. Runtime secrets are environment-only; late delivery/rotation requires controlled restart unless already injected before HTTP startup.
4. Standard and Approval have the same safe foundation features in M1. Identity/SSO remains the conditional M2 PoC; business authorization, Orders, approvals, plan transitions, backup/restore and purge are not implemented by this milestone.
5. The current read-only readiness path performs fresh database checks; this is not a load/performance certification or an M6 hardening/backup acceptance record.

Owner review must confirm security boundaries, migration ownership, failure reconciliation and the single-operations-host constraint before merging. The roadmap/ADRs have not been marked owner-approved by the implementation agent.
