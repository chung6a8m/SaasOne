## Requirements mapped to proof

| Requirement | Implementation and evidence |
|---|---|
| Frozen domain/extension contract | Plan and contract-first policy tests preceded implementation. `OrderPolicy`, `OrderPermissions` and immutable submission/decision records define state, revision, marker and current replay authorization. |
| Ownership and tenant isolation | Native shell selects the connection; tenant/actor/client cannot be overposted. Tests cover Own/Others Deny, filtered pagination, cross-tenant resource IDs and token binding. |
| One UI/API service | Encoded antiforgery pages and strict v1 API call `OrderService`; native tests cover successful writes, stale revisions, default-deny/current overrides, cross-transport replay and maximum valid Unicode. |
| Atomic business/audit/replay | Orders, revision snapshot, enlisted handler writes, audit and receipt use the existing single connection/transaction coordinator. Real audit CHECK/permission failures and a handler write-then-fail fixture leave no partial effect. |
| Optimistic concurrency | SQL rowversion plus monotonically increasing revision; immutable creator/history; two different keys on one revision have one winner, not a silent overwrite. |
| Safe idempotency | Same-key races execute once; different payload conflicts only after current authorization; lost Create/Submit responses and Edit replay after later revisions return the committed snapshot without new side effects. Tenant/actor/client partitions and expiry tombstones are tested. |
| Current replay access | Revoked action, read permission, entitlement or membership denies replay. Issuer/platform/account/membership/ACL source outages fail closed before returning stored data; fresh authorization is repeated after serialization. |
| Retained approval obligation | Standard confirms only without a marker. Missing handler cannot fall back. Fixture Reject/edit/resubmit/decision validates revision binding and marker retention; persisted reader counts pending/rejected/rework independently of current entitlement/handler. |
| Private installation/recovery boundaries | Verified M3 upgrade preserves ACL; installed missing-marker and unknown future-profile cases stay closed. The real Orders reader blocks downgrade until confirmation. Runtime cannot rewrite history/receipts/audit, delete orders, administer SQL or expose decision/CMS routes. |
| Migration ownership | Orders owns its `orders` stream; Auditing owns the nullable business-detail extension. Tenancy/Access/native ownership is unchanged; snapshot and architecture checks remain mandatory. |

M4 approval hooks are explicit fixtures, not an M5 implementation. M5 must repeat the relevant races and atomicity tests with its actual request/decision tables and integrate their recovery reader into the closed product inventory.

## Operational and product choices awaiting owner review

The minimal order fields, compiled product-module composition and seven-day replay retention are proposals, not previously confirmed business requirements. Expired receipts remain tombstones; storage growth and retention of order snapshots/audit details require operational policy. UI screens are functional and script-free, not a finished product design system.

Follow the [Orders runbook](../runbooks/m4-orders.md) and [ADR 0007](../adr/0007-orders-command-contract.md) before rollout. Existing M3 customers require private profile-v2 reconciliation and explicit Orders permission grants. M4 registers no production approval handler: an Approval-required Submit deliberately returns 503 without confirming the order. M5, M6 and M7 remain separate milestones.
