# M4 Orders Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task. Checkboxes below track implementation, not owner acceptance.

**Goal:** Deliver tenant-isolated Orders through the existing native identity host, with one application service for UI/API, atomic audit, optimistic concurrency, safe replay and an entitlement-independent recovery reader.

**Architecture:** `src/Modules/SaaS.Orders` is a compiled business module composed by the product host, following M3's explicit application endpoint allowlist. It consumes the existing platform transaction/access contracts, never the future Approvals implementation. The host privately installs its EF stream under M3 resource ownership and the durable write gate; HTTP never installs or repairs schema.

**Tech Stack:** Repository-pinned .NET 10 / EF Core 10 / Orchard Core 3.0.1 / SQL Server. No new version selection.

**Spec:** `docs/roadmap/saas-orchard-roadmap-v1.md` revision 1.3, sections 4, 5.2, 5.6, 6.1–6.3 and M4. ADR 0002–0006 remain subject to owner review; this plan does not promote their status.

## Locked implementation choices (proposals for owner review)

### Data and state

A minimal order contains a tenant-local unique Number, CustomerName, Amount, Currency and plain-text Notes. These are implementation scope choices, not previously confirmed product fields; line items, tax, payment, cancellation and deleting orders are out of scope. Number is 1–64 ASCII letters/digits/dot/dash/underscore, normalized upper-case. CustomerName is 1–160 characters; Notes is at most 2000; currency is three ASCII uppercase letters (not a claim of an ISO catalog). Amount is nonnegative decimal(18,2). Strings are NFC normalized, trimmed and line endings normalized. No HTML or uploads.

Orders own a monotonically increasing bigint Revision and SQL rowversion; every successful edit or transition increments Revision exactly once. Create is revision 1 / Draft / ApprovalRequired=false. Edit is only Draft or Rejected and returns Draft, preserving ApprovalRequired. Submit is only Draft: Standard plus marker=false becomes Confirmed; current Approval entitlement OR marker=true requires an enabled, ready approval handler and becomes PendingApproval. Missing entitlement, handler or schema never falls back to Confirmed. PendingApproval and Confirmed content is immutable. Approval decisions match current revision and rowversion, cannot be made by the creator, require a reason for Reject, and preserve the marker. Each successful mutation appends an immutable revision snapshot.

### Contracts and transaction lifetime

- `OrderDraft`, `OrderCommand`, `OrderView`, `OrderCommandResult`, `OrderAction`, `OrderStatus` in `src/Modules/SaaS.Orders/OrderContracts.cs`.
- `OrderService.ExecuteAsync(OrderCommand, CancellationToken)`, `GetAsync(Guid, CancellationToken)` and bounded `ListAsync(int, CancellationToken)` share one policy implementation.
- `OrderAccessContext(CurrentAccess, AccessSnapshot, string ClientId)` is supplied by trusted host composition using a new transaction-bound `AccessService.ReadForAuthorizationAsync` method. Authentication/current platform authority and tenant ACL are read again after serialization.
- `IOrderApprovalHandler.DemandReadyAsync`, `SubmittedAsync` and `DecidedAsync` receive the caller-owned `TenantTransaction`. They must enlist, await all work, and never commit, open another connection or independently retry. M4 registers NO production handler and exposes NO public decision endpoints; SQL fixtures demonstrate the contract, M5 implements it.
- Order update, revision history, optional handler writes, business audit and command receipt use that one physical connection/transaction. SQL/app-lock ordering is write gate, access snapshot, receipt partition, resource; locks survive until commit/rollback.
- `OrdersObligationReader : IApprovalObligationReader` verifies DB identity, migration/schema and marker/state integrity and counts `ApprovalRequired && Status != Confirmed`, without depending on current entitlement or handler registration. Unknown/missing state/schema fails closed. The host's table allowlist remains closed to unfamiliar business tables.

### Authorization and replay mapping

Definitions: `Orders.Create`, `Orders.ViewOwn`, `Orders.ViewOthers`, `Orders.EditOwn`, `Orders.EditOthers`, `Orders.SubmitOwn`, `Orders.SubmitOthers`, `OrderApprovals.Decide`. Own/others is selected using the persisted creator. A Deny on the selected permission cannot be bypassed by trying the alternate permission. All Orders policies require the Orders entitlement; decisions also require Approval.

Create requires Create and ViewOwn. Edit requires the selected Edit and selected View. Submit requires the selected Submit and selected View. Approve/Reject require Decide, selected View and actor != persisted creator. Replay uses exactly those current action/read/creator rules, but NOT state, revision or rowversion preconditions for a new execution. Authorization precedes disclosure of stored results, expiration or fingerprint conflict. A missing or revoked source fails closed.

Idempotency partition is TenantId + authenticated actor + authenticated client + action + case-sensitive key. Keys are bounded ASCII (8–128 characters). SHA-256 encodes the partition and normalized request; fingerprint includes the original resource ID, payload, expected Revision and rowversion, never their current replacements. The result snapshot is saved atomically with the mutation. A transaction-owned per-partition lock and unique primary key serialize duplicates. After acquiring it, reload current authority and check committed receipts before new-command preconditions. A different payload returns 409 only after current replay policy passes. Replay never writes a second business audit/history/handler side effect.

Replay window is seven days from commit. Expired receipts remain tombstones and return an authorized 409 `idempotency_expired`; keys are not silently reused. M4 has no automatic receipt deletion. Retention growth and future maintenance are explicit operational tradeoffs, not an infinite replay guarantee.

### Host/install/UI

The existing private `access-install` / plan reconciler installs the product's Orders stream under the closed gate and grants runtime only required DML. Application profile version/hash advances explicitly; stale deployments fail readiness until private reconciliation. Initial installation accepts a verified foundation with no business tables; an installed Orders profile with missing schema is not treated as empty history. Recovery reads persisted Orders even with no handler.

API: GET/POST `/{tenant}/api/v1/orders`, GET `/{tenant}/api/v1/orders/{id}`, POST `.../{id}/edit` and `.../{id}/submit`. POST uses bounded strict JSON, a required Idempotency-Key, and expected revision/token for existing orders. Unrecognized tenant/owner/marker/state fields are rejected, not bound. Web paths mirror `/orders`, `/orders/new`, `/orders/{id}` and its actions with encoded HTML and antiforgery. The native issuer/cookie/bearer boundaries are unchanged. UI/API use identical service outcomes (401/403/409/503); web success redirects to the same resource. Pagination is bounded and must not reveal another owner's records or counts.

## Review focus

1. Duplicate requests after state/token changes must replay without executing preconditions; denied resource/action access must reveal neither result nor fingerprint conflict.
2. Missing approval handler/schema/marker must never turn a required-approval order into Confirmed, including Rejected -> Draft.
3. Audit/handler failures and ambiguous client retries must not leave partial orders, receipts or history.
4. Tenant/actor/client partitions and persisted ownership must prevent cross-context key/resource discovery; forged payload properties cannot select connections or marker state.
5. Gate-close races, schema corruption, unexpected table inventory, runtime SQL privileges and same-SHA evidence cannot be weakened by a happy-path test.
