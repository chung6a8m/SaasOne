# Issue #15 P3 — bounded List integrity projection while preserving all 51 resource locks

Status: diagnostic-backed, test-first optimization candidate, not performance/production acceptance.
Base: `92808f51fe43f124d51d496fd636132a102c984a` (stacked PR #17, which depends on Draft PR #16). No independent merge or deployment allowed before its parents' security approval.

## Evidence and hypothesis

Operation-specific SQL/HTTPS M7 profiling in PR #17 ([run 42957974621](https://github.com/chung6a8m/SaasOne/actions/runs/42957974621), [artifact 13827663032](https://github.com/chung6a8m/SaasOne/actions/runs/42957974621/artifacts/13827663032)) identifies high List page-lock acquisition/hold p95. Example alpha List lock wait ~1,598 ms and approximate page-lock acquired→transaction end hold ~2,390 ms. This diagnostic includes ramp/drain and is **not** matched SQL-server lock-owner or SLO proof.

After the already-ordered 51 shared resource locks, `OrderService.LoadPageAsync` currently performs **three SQL SELECTs**, separately retrieving rows, latest snapshot/revision and all-history count/approval marker. Including the pre-lock page-ID query, the real SQL test records **four Orders/Revisions SELECTs per full List page**. Hypothesis: one bounded EF Core SQL Server projection after the locks can retrieve all three sets of integrity facts in one SQL query, for **2 total Orders/Revisions SELECTs** with unchanged locked state. This is a reduction in round trips, not an automatic performance win; query plan/correlated scans might be slower. If lock hold/wait worsens materially, revert.

### Observed RED performance regression — candidate rejected pending safer query (2026-11-11)

Real pinned SQL Server [M4 components run 42977182511](https://github.com/chung6a8m/SaasOne/actions/runs/42977182511), [artifact 13835503347](https://github.com/chung6a8m/SaasOne/actions/runs/42977182511/artifacts/13835503347): the initial P3 correlated `LongCount`/`Any` projection is **NOT** acceptable at history depth. For 51 full-page orders, per-order 50 revisions: projection **1,287 logical reads / 6ms CPU**, old three queries **669 reads / 2ms CPU**. For 1,000 revisions: projection **16,042 reads / 85ms CPU**, legacy **5,556 reads / 37ms CPU**. The test now requires the candidate to have no MORE actual SQL Server logical reads than the legacy three-query equivalent at both depths, while retaining the unchanged two-SELECT public List contract, all shared locks and fresh ACL/history integrity guards. Any failure is a real **RED performance-regression gate**, not to be hidden by changing test thresholds or accepting command-count alone. Investigate a single joined, set-based grouped summary or revert P3 if no scalable one-query variant can be demonstrated.

### Follow-up correction after real RED: grouped joined history projection

[RED pinned M4 SQL run 42978080735](https://github.com/chung6a8m/SaasOne/actions/runs/42978080735) at test-only commit `85512b5deb4468bc902c9dd6b48eb5bf51845b1a` built successfully, 45/46 tests passed, exactly the full-page List test failed `Deep-history projection read amplification at depth=50: projection 1287, legacy 669`. The earlier 1000-revision unguarded evidence was 16,042 vs 5,556. The runtime fix replaces correlated `LongCount`/`Any` with **one joined, grouped summary of all selected revisions**, plus a LEFT JOIN to the exact latest revision. Left joins preserve the previous 503 on missing historical/current revision rather than misreporting 404. The existing 51 ordered Shared resource locks, post-lock fresh ACL, all snapshots/markers and 2 Orders/Revisions SELECT requirement remain unchanged. The test-only SQL comparator uses the same new EF LINQ shape and asserts actual SQL Server logical reads no greater than the prior three-query approach at 50 AND 1000 revisions per order, capturing CPU/SHOWPLAN operator evidence separately. This is a real-SQL regression threshold, not a rewritten M7 performance SLO.
