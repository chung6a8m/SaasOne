## Evidence and hypothesis

At head `f0b71ddecb12c8ea93c62b943fdd359d11485bb8`, PR synthetic merge `1c1f0992f9e57cf22220464215f29f7b97bc02f6`, [M7 Candidate run 42570281448](https://github.com/chung6a8m/SaasOne/actions/runs/42570281448), [artifact 13653231938](https://github.com/chung6a8m/SaasOne/actions/runs/42570281448/artifacts/13653231938): 1,845 successful requests and no unexpected request failure, ~25.7561 physical SQL opens/request, ~119.9333 commands/request, 22/22 performance cells and 88/88 metrics FAIL. The privacy-safe `identity.native` stage records **16,056 opens** (~8.70/request), exactly twice the **8,028** fresh issuer-family validations. Source confirms that each `IdentityProtocol.AuthenticateBearerAsync` calls `IdentityAuthority.ValidateAsync` (native account + authorization in one Default scope), then `DefaultIssuerStore.ValidateAccessAsync` (token + authorization in another Default scope). These are sequential *fresh* reads, not independent permissions to cache.

**Narrow hypothesis:** a *single new native issuer scope per one bearer validation*, performing **all** account/lockout/stamp, authorization/status/subject/invalid-access-index and token/type/status/binding/expiry/application checks in the existing order, saves one **physical native login per fresh bearer validation** without reducing any source checks. The scope is never shared across subsequent validations, HTTP requests or ACL/Orders lock boundaries. As with any SQL query, concurrent revocation can occur after the last source read; no cross-call authoritative state is held or cached.

## Task boundaries

**Affected runtime:** `src/Platform/SaaS.Identity/DefaultIssuerStore.cs`, `IdentityAuthority.cs`, `IdentityProtocol.cs`. **Tests:** `tests/Unit/SaaS.UnitTests/IdentityPoc/IdentityNativeScopeTests.cs` (existing nonmandatory M2 SQL test name, no mandatory inventory modifications). **Plan and evidence:** this file plus `docs/verification/m7-native-bearer-scope.md`.

**Interfaces consumed:** `IdentityAuthority.ValidateAsync` and `IdentityProtocol.DemandClaims`, fresh unpooled platform context, new independently owned Default issuer `IShellHost` scope, native UserManager, OpenIddict AuthorizationManager, TokenManager, and fresh YesSql invalid-access index query. **Provided:** internal `IdentityAuthority.ValidateBearerAsync(familyId, routedTenantId, principal, tokenId, ct)`, internal `DefaultIssuerStore.ValidateBearerAsync(subject, stamp, authorizationId, tokenId, afterAuthorizationCheck, ct)`. The synchronous callback performs only the same principal/family `DemandClaims` binding at its original position between native authorization validation and native access-token validation. Existing `IdentityAuthority.ValidateAsync` (including web), standalone `DefaultIssuerStore.ValidateAccessAsync`, login, authorization grants and refresh behavior must remain unchanged.

**Security/order:** JWT signature/issuer/audience/scope/lifetime validated before source lookup. Then fresh platform family/session/account/tenant/membership/security/client checks, native enabled-account/lockout/security-stamp checks, native authorization status/subject/invalid-access-index checks; then principal/family claim binding; then native token validity/type/subject/authorization/application/expiration and authorization check **within that same new native scope**. Never suppress or replace any of these with claims-only Allow. No caching across validations; native entity caching stays disabled. Existing post-lock issuer+ACL reads, Deny, tenant routing, transaction ownership and Orders/Approvals audit/rollback are untouched. No migration/index/schema/role/secret/timeout/connection-string change.
