# M7: keep per-transaction customer profile checks on the already-owned Orders SQL connection

**Date:** 2026-11-09. **Milestone status:** M7 Candidate FAIL, PR #14 Draft/unmerged, Issue #12 OPEN. This task is a narrow proposed optimization with real-SQL RED before GREEN, not a change to 100 VUs or the approved 22-cell/88-metric targets.

## Source-locked measurements and design choice

At HEAD `bec251204813b2db02f1e1a47de6a1936a392cb5`, [M7 run 42589726144](https://github.com/chung6a8m/SaasOne/actions/runs/42589726144), [artifact 13660888081](https://github.com/chung6a8m/SaasOne/actions/runs/42589726144/artifacts/13660888081), the synthetic PR merge is `acec1001418fabdcd1a6f9104bfea5d097218ef3`: 2,665/2,665 successful all-phase HTTPS requests, mandatory 7/7 SQL/HTTPS, 27/27 architecture, 201/201 unit, **22/22 cells and 86/88 metrics FAIL**. SQL diagnostic shows 40,366 opens (**15.1467167/request**), ~107.8116 application SQL commands/request. `acl.authorize` has **7,237** observed invocations and **7,237** physical customer opens, each taking ~306ms mean; resource/page lock wait p95 ~2.046/3.577s, command-lock hold p95 ~4.676s.

The product-host `OrdersEndpoints` calls `ApplicationRequestAuthority.ReadAsync` for every post-lock `TransactionAccessReader.ReadAsync` authority refresh. The platform/native issuer is checked afresh, but then `ApplicationAccessProfile.VerifyAsync` opens a **new, unpooled customer connection** to read the five exact EF histories, ApprovalHistory columns and current tenant profile, while `OrderService` already owns a customer SQL connection and an active transaction on the *same selected tenant*. This adds a separate physical login/request for each post-lock check and may create additional session scheduling pressure.

**Hypothesis:** keep the full, fresh product-profile SQL reads on the caller-owned connection **enlisted in its current transaction**. Avoid only the redundant physical login; do **not** cache a verified plan, omit a migration-history comparison, infer tenant from a token, remove a live ACL/native recheck, weaken isolation or extend an existing connection beyond the transaction. Expected `acl.authorize` opens per invocation: **1 → 0** (application profile still issues commands on the Orders transaction). The initial `ApplicationRequestAuthority.ReadAsync` outside the transaction still owns and disposes its own fresh customer connection.

## Concrete files, consumed and provided contracts

**Runtime**:
- `src/SaaS.Web/Access/ApplicationAccessProfile.cs`: add a safe overload `VerifyAsync(Guid, string, DbConnection, DbTransaction?, CancellationToken)` accepting only an *already-open* caller-owned connection and the transaction belonging to that connection; retain original four-argument `VerifyAsync` API for nontransactional callers. Enlist each SQL client command in the supplied transaction (five-history UNION, ApprovalHistory column probe) and the EF `TenancyDbContext` profile query through `Database.UseTransactionAsync`. Keep complete fresh expected/applied histories, row ceiling/fail-closed checks, exact tenantId/plan/version/hash and all existing exception semantics. Never commit/rollback/dispose the transaction or connection here.
- `src/SaaS.Web/Access/ApplicationRequestAuthority.cs`: add optional trusted `TenantTransaction` parameter to `ReadAsync`. If absent, preserve existing owned connection logic. If present, verify the transaction is enlisted in the same open customer SQL connection and it matches the already-routed fixed customer server/catalog/principal. Pass that transaction to `ApplicationAccessProfile.VerifyAsync`. All platform/native account/issuer/membership, tenant status/registry/generation, clientId and current plan checks still execute freshly per invocation.
- `src/SaaS.Web/Orders/OrdersEndpoints.cs`: pass the existing trusted `tx` only in the `TransactionAccessReader.ReadAsync` current-authority callback. Initial public ARA access stays without transaction, web and API use the same current-profile validation, no platform dependency on Orders.

- `tests/Unit/SaaS.UnitTests/M4NativeHttpTests.cs` in the existing mandatory `Native_required_authority_sources_fail_closed_before_returning_a_stored_result` case: verify a temporarily corrupted `tenancy.ApplicationProfile.ManifestHash` returns 503 for both fresh API and web, even on a warm transaction with an already-open connection; restore the exact original value in `finally`, then assert healthy replay works. Do not disclose SQL/credential information or leave the fixture corrupted. Other M2/M3/M4/M5/M6 mandatory security, history, replay, idempotency, audit and rollback tests remain unchanged.

**Owner/migration:** Tenant migration streams unchanged; all five owners still verified, no schema or index. SQL runtime roles and `Pooling=False` unchanged. No tenant routing, app-lock order/mode/timeout, command-lock hold lifetime, transaction isolation, retry or connection lifetime change across requests. No per-request or cross-request cached Allow. Unauthorized/invalid source must fail closed with 401/403/503 as before.
