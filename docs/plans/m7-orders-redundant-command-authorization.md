# M7 — shorten Orders command-lock hold without removing post-resource authority (2026-11-09)

**Status:** proposed narrow RED–GREEN change only; PR #14 stays Draft, Issue #12 OPEN. The already-approved M7 100-VU/four-active-tenant workload and 22-cell/88-metric budgets are immutable.

## Measured source-matched problem

At head `27bb76487d68b920e2e64879b961e7461fce4cc3`, exact PR synthetic-merge Candidate `0a26a646fa6b179d2cd3251e30692d5ddabce106`, [M7 run 42584504507](https://github.com/chung6a8m/SaasOne/actions/runs/42584504507), artifact `13659006116`: 2,540 successful all-phase HTTPS requests, 0 unexpected failures/integrity errors; 17.04646 unpooled physical SQL opens/request, 119.83937 application SQL commands/request. Approved performance fails **22/22 cells and 88/88 metrics**. SQL stage profile has **1,608 `orders.write`** operations, 1,608 command-lock waits and 2,074 resource-lock waits. Measured p95 command-lock acquired-to-transaction-end hold is approximately **6,776ms**; page-lock wait p95 **3,996ms** and resource-lock wait p95 **2,810ms**, with SQL APPLICATION/KEY contention. These are overlapping stage measurements, not SQL-server-confirmed lock ownership/CPU.

`OrderService.ExecuteAsync` performs: (1) fresh Access before partition/command lock, (2) another fresh Access immediately **after command lock**, (3) a *later* fresh Access immediately **after resource lock** in either receipt or new-command branch, and (4) a fresh Access again after the optional approval handler and before audit/receipt. The second call is followed unconditionally by the third before any permission decision, receipt disclosure/fingerprint conflict or business write. It increases command-lock hold via a full platform/native/customer ACL revalidation and its ~three independent SQL logins.

**Hypothesis:** remove only intermediate call (2), retain (1), (3), (4) and the same identity/tenant/source checks. This eliminates **one complete, redundant source-fresh authorization cycle per Orders write**, reducing physical logins/request and time inside command lock. No cache of a prior Allow is introduced, no decision is made using the initial context after the resource lock, and native/ACL revocation after either lock remains visible at the existing post-resource check.

## Files, contracts and security

- Runtime: `src/Modules/SaaS.Orders/OrderService.cs`, `ExecuteAsync` only. Replace post-command-lock `AccessAsync(tx)`/SameIdentity with a declaration assigned in **both** mutually exclusive receipt/new branches by their existing post-resource-lock `AccessAsync`/SameIdentity. Every `OrderPermissions.Require` / `RequireRead` still consumes that later fresh context; the last recheck before audit remains. `OrderService.ReadAsync`, List, CanDecide, DemandCreate, TenantWriteGate, SqlTransactionLocks, transaction, idempotency/receipts, resource lock order and approval-handler boundaries unchanged.
- Test-first: modify only the existing mandatory `M4OrderSqlTests` cases `Create_persists_one_order_revision_audit_and_receipt_and_reads_the_same_rowversion` and `Revoked_action_denies_replay_before_disclosing_a_result_or_fingerprint_conflict`; add test-only currentAccess invocation count and optional per-read mutation hook to `M4SqlHarness` in the same file. No new mandatory SQL case names, no missing/skipped test.
- Positive creation must still persist precisely one revision/audit/receipt, use one transaction-owned SQL login and perform **three** fresh current-authority reads (initial, after resource lock, final). On the unoptimized source it performs **four**, a deliberate real-SQL RED assertion.
- Negative replay and new write: inject fresh role Deny or identity change **between initial validation and the later resource-locked recheck**; both must fail 403/401 without receipt/result/fingerprint disclosure and with no new revision, order, receipt or business audit. Source failure still fails 503. Existing mandatory test matrix enforces same-key one-winner/last response, changed payload, revision conflicts, approval handler rollback, source revocation, closed WriteGate, cross-client partition, resource ownership and history integrity.
- Source-freshness: no results cached across authorization boundaries. The first access still controls the partition only; the later access after resource lock authorizes any receipt/result and every new-command mutation, and `SameIdentity(initial, later)` still enforces TenantId/UserId/ClientId stability. If a command receives an unexpected receipt resource, the resource lock must still be acquired before the check. The final access after handler still sees mid-handler security revocation before audit/receipt.
- Database migration owner: **none**. No SQL DDL/index, password/config, role, provider, connection pool, timeout, isolation, global lock, tenant routing, app lock name/mode or target change.
