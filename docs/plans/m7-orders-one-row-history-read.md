`OrderService.LoadAsync`, called by the protected `ReadAsync` and `ExecuteAsync` after the transaction-owned resource lock, currently performs **one tracked Orders row SELECT**, **one latest revision SELECT**, **one revision LongCount SELECT**, and (when `!ApprovalRequired`) **one historical approval marker EXISTS SELECT**. All four reads are sequential on the same enlisted transaction connection. This extends resource lock hold and increases command traffic without adding source-freshness—these statements read the same database in one transaction. The rowversion and expected revision still must be enforced on write.

## Locked change contract

**Files:** `src/Modules/SaaS.Orders/OrderService.cs` (`LoadAsync` only); `tests/Unit/SaaS.UnitTests/M4OrderSqlTests.cs` (existing exact-inventory Create and Standard_submit tests); optional evidence ledger in `docs/verification/m7-orders-one-row-history-read.md` after real CI. Migration owner: **none**. No SQL DDL, index, schema, provider, connection/transaction lifetime or role/permission change.

**Provided:** one EF Core SQL command returning *tracked* `OrderRow` and *as-no-tracking* latest revision, plus **fresh SQL-side** revision count and historical-approval presence for the same persisted OrderId. Use `OrdersDbContext.Orders` projection with scalar correlated queries on `OrdersDbContext.Revisions`, preserve the current row entity as tracked for `SaveChangesAsync` and optimistic `rowversion`. Do not construct or attach a new OrderRow, use EF InMemory, drop any check or evaluate history in a local cached list.

**Invariants:** The exact current `OrderPolicy.DemandIntegrity(current)` and later status/ApprovalRequired/snapshot equality, `HistoryCount == Revision`, and `!ApprovalRequired && HistoricalApprovalMarker` denial stay. Missing row => original `AccessDeniedException(404,"order_not_found")`; corrupt/missing latest revision, malformed snapshot, count mismatch or historical marker => `AccessDeniedException(503,"order_history_invalid")`. Preserve the existing error ordering (row integrity before history denial), Deny, current authority after resource lock, SameIdentity, tenant/application profile, replay semantics, WriteGate, ordered transaction-owned locks, approval-handler rollback, receipt + revision + audit atomic commit and no retries.

**Review issue:** EF projection must translate to one SQL SELECT on real SQL Server and keep OrderRow tracked; a translated scalar subquery or latest-revision outer apply is acceptable. If projection translates to multiple SQL commands or entity becomes untracked, do not claim GREEN. The project already constrains orders to unique (OrderId,Revision) revision rows. It is acceptable for EF to read all four facts in one SQL statement; it is not acceptable to skip the historical obligation or silently return a row on missing/invalid history.
