## Non-negotiable security/consistency contract

1. **Fresh authorization:** each initial or post-resource-lock `IdentityAuthority` validation must actually read family/session/account/tenant/membership/security/client, native enabled-account/stamp/lockout/authorization/token and post-native tenant; ACL Deny and full profile/history remain freshly checked. There is no HTTP/request/AsyncLocal/DI cache of an Allow, `IdentityFamily`, `CurrentAccess`, `ClaimsPrincipal`, native YesSQL entity or EF tracked tenant. Claims never choose a database.
2. **Source and principal freshness:** the existing M2 source-disabled-between-validations regression MUST remain green, *including two validations within one DI/HTTP context*. A SQL Server session authenticated before `ALTER LOGIN ... DISABLE` does **not** provide the same guarantee as a subsequent new physical login. Merely calling `ChangeDatabase`, clearing EF change tracking, `SELECT ORIGINAL_LOGIN()`, or issuing another SELECT on that existing session is not proof of login revocation. Do not silently relax this contract.
3. **Tenant isolation:** routing establishes server, catalog, tenant nonce, migration and baseline against fixed deployment secrets; a request feature or token cannot retarget a borrowed session. Never borrow a platform session as customer or vice versa; cross-tenant reuse must fail closed. Account shared across alpha/beta does not imply a shared authority source or plan.
4. **Transactions:** Orders owns exactly one tenant SQL connection and `SqlTransaction`; profile/ACL/Orders/Approvals histories that already borrow it remain sequential, enlisted, and caller-owned. Never lend a transaction-bearing customer connection to native/platform work or another HTTP request; do not close/commit/rollback a caller's transaction. Keep write gate, command/resource/page/ACL app-lock ordering, rowversion, history, audit/receipt and rollback.
5. **Resource lifetime:** no open SQL connection across request-body/form waits, between requests, or beyond the owning stage. The routing platform/customer transports are disposed **before** Orchard and downstream processing. `Pooling=False`, `Enlist=False`, fixed runtime principal and deployment source validation remain unchanged. On cancellation, exceptions, plan change or shell reload, dispose/abort the candidate lease and fail closed. Prevent overlapping commands on a single connection, including nested native service calls.
6. **Reviewable safety evidence:** a claimed saving must distinguish physical SqlClient `ConnectionOpenAfter` events from commands, and count opens by routing, fresh platform validation, native validation and Orders lock phase on the same **source SHA**. Never label a Candidate failure as Accepted or compare different-source Full runs as final evidence.

## Options and decision gate

| Candidate | Possible saving | Risk / disposition |
| --- | --- | --- |
| Global `Pooling=True` or a cross-request/tenant connection or Allow cache | Superficially large | **REJECTED**: alters principal/source revocation and isolation guarantees |
| Reuse one open platform/native session across *multiple* initial/post-lock validations in a request | Multiple logins | **BLOCKED**: SQL login disabled after first validation can still operate on existing session; resource-lock wait extends session life; fresh native scopes are part of current security contract |
| Share a SQL transport *inside one* full platform+native validation only, then dispose before next validation | Potentially one platform/native open per validation | **RESEARCH ONLY**: both stores currently own separate transports. Must prove actual native YesSQL/Orchard store can borrow this **exact fixed-source, same-principal** connection without changing native state, its transaction/session lifetime, lock ordering, EF ownership or native invalid-access checks; unsupported adapters/direct SQL replacement are prohibited |
| Keep current explicit one-open-per-validation and owner transaction borrowing | Zero immediate saving | **SAFE BASELINE** retained until a narrower mechanism passes review and a genuine RED→GREEN SQL test |

**Decision for this change set:** commit this contract and *add tests only*. Do not introduce a request lease/provider yet. Any runtime proposal must first name the precise pair of sequential opens to merge, supply the actual SqlClient/YesSQL ownership API, estimate the target reduction from measured stage counts, and secure review for source-disable semantics. If this cannot be shown without weakening the M2/M4/M7 gates, abandon the reuse candidate and profile Orders lock ownership instead.
