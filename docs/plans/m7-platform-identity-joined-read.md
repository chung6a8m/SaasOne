At head `6c514a2cde7119db69ae02729f71ce17acd68054`, M7 same-source PR synthetic merge `d463e43056d4e6ef364ee5249b491af9398ee8e1`, [Candidate run 42601565547](https://github.com/chung6a8m/SaasOne/actions/runs/42601565547) attempts 1 and 2 (artifacts `13665759547`, `13666414420`): all 12 inherited M0–M6 workflows succeed and both M7 runs pass 7/7 mandatory real SQL/HTTPS, 201/201 non-SQL unit, 27/27 architecture and zero unexpected HTTP/integrity failures. Independent artifact comparison: 12.4307 vs 12.4318 physical opens/request, 106.0693 vs 106.0856 application commands/request, 2,452 vs 2,513 successful requests. The client diagnostic attributes **8 SQL commands and one physical platform login** to every `identity.fresh` stage (7 sequential family/session/account/tenant/membership/security/client reads, then a second current tenant plan read AFTER native bearer checks); also one independent fresh native issuer SQL login and five native commands. With 9,110–9,338 `identity.fresh` stages per run, this is a substantial serial SQL-command cost.

**Narrow choice:** fetch the seven initial source-of-authority entities in **one server-side EF Core SELECT with key-based LEFT JOINs**. Keep all exact validation predicates, errors, fresh connection, native issuer validation, post-native tenant SELECT and per-request/per-post-lock revalidation. This **does not** avoid a native check, allow authority caching, remove a query needed after a mutation, or change any SQL credentials/pooling/transaction.

## Source contracts and review risks

**Files:** `src/Platform/SaaS.Identity/IdentityAuthority.cs` (`ValidateCoreAsync` only); `tests/Unit/SaaS.UnitTests/IdentityPoc/IdentityConnectionLifetimeTests.cs` (existing SqlM2 test only). No migration/index/schema/role, native issuer, website, ACL, Orders app locks, transaction, receipt/audit or workload change. Migration owner: none.

**Consumed:** one owned `PlatformDbContext` using `connections.Platform("runtime")`; EF Core `AsNoTracking` queries for `IdentityFamilies` (root unique Id), `IdentitySessions` (family.SessionId), `IdentityAccounts` (family.GlobalUserId), `Tenants` (family.TenantId), `IdentityMemberships` composite (family.GlobalUserId, family.TenantId), `IdentityTenantSecurity` (family.TenantId), `IdentityClients` (family.ClientId). All keys come from persisted current family, never HTTP claims or token-selected sources.

**Provided:** one `SingleOrDefaultAsync` projection with `Family`, `Session`, `Account`, `Tenant`, `Member`, `Security`, `Client`. Use LEFT JOIN only for missing-row **fail closed** behavior; unique PK constraints guarantee no duplicates. Reapply every existing test in its original order. A missing family or wrong family/issuer/expiry remains 401 `grant_invalid`; missing required session/account/tenant/security/client remains a dependency error (not an Allow). Missing/inactive member remains 403 `tenant_access_denied`; generation and revoked account/session/client remain denied with the original codes. Keep the original native UserManager account/lockout/stamp and OpenIddict authorization/token checks **after** fresh platform checks and keep `DemandClaims` at the same point inside native scope. Then keep the **separate fresh AsNoTracking tenant SELECT AFTER native validation** for product API. No cross-validation snapshot, cached Allow, shared connection, or weakened rollback.

**Risk:** reading seven sources in a single SQL statement changes the inter-query timing. All data comes from the same fresh SQL Server statement and source; revoke-before-next-call must deny on the next call, including membership, native account, authorization, token and client. A mid-query concurrent mutation does not become serializable just because reads are joined; do not claim guaranteed cross-database revocation linearizability. Joins must not inadvertently convert missing membership into success or turn a missing security/client record into Allowed; correct provider translation must be proven on real pinned SQL Server.
