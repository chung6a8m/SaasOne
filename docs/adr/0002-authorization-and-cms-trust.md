# ADR 0002 — Authorization and same-origin CMS trust

Status: Proposed for owner review; reviewed roadmap constraints retained. Owners: access-control and security implementers. Scope: R01, R03; roadmap §3.3, §4.2–4.4.

Authorization requires valid account/session/grant and generations, an operational tenant, current membership, entitlement/feature, an Allow source, no RoleDeny or UserDeny, and the resource rule. Unspecified is not explicit Deny but cannot grant access. Deny is a mandatory policy failure (`context.Fail()` or equivalent), not merely absence of Succeed. Manager/Accountant/Sales never imply Orchard Administrator. PlatformOperator lifecycle authority does not imply reading Orders. Membership/role/override administration must prevent self-escalation and be audited.

Each authorization beginning after an authoritative revocation commit reads the new state from the authoritative platform, issuer and required tenant sources. No cross-request cached Allow or role claims as authority; same-request memoization only. An already-authorized request may finish under its transaction except the stricter plan-change drain protocol. Deferred execution and retries reauthorize. Missing required sources return dependency-unavailable with correlation ID and no business access; invalid credentials return 401, policy denial 403, dependency failure 503. UI uses the same outcomes without redirect loops or cross-tenant disclosure.

Path prefixes, database isolation and cookie Path do not isolate browser origins. All modules, recipes, features, scripts, Razor/Liquid templates and themes are platform-published code. Tenant users cannot edit them through UI or direct APIs. Provision recipes use minimal feature allowlists, not all-CMS defaults. Default content is encoded text/structured data.

**M0 content policy:** customer uploads and rich text are disabled; allowed customer-upload file types and publish privileges are therefore the empty set. No customer HTML, SVG, JavaScript, executable content or inline object uploads are served on the application origin. Platform-owned static CSS/images/scripts are shipped with the reviewed build. Any future upload must have a reviewed allowlist, server validation/sanitization, explicit content type, attachment delivery or a separate non-application origin, and authorization/negative tests before enablement. CSP supplements, not replaces, this trust boundary.

Alternatives rejected: arbitrary tenant scripts on shared origin, relying only on cookie Path, or using Orchard Administrator for convenience. A requirement for arbitrary executable customer content requires an origin-boundary redesign. M1 proves recipe/bootstrap/direct-API restrictions; M3 proves role/override changes cannot reopen them and tests post-commit revocation/source failures.
