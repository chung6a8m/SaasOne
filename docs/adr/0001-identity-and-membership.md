# ADR 0001 — Central identity and tenant membership

Status: **Conditional — M2 native PoC demonstrated; owner architecture/security acceptance pending**. Owner: project owner / identity implementer. Scope: R02, R03; roadmap §3, §4.1–4.4. Lifetime defaults below are implemented candidates for owner review, not an approval inferred from CI.

## Decision and alternatives

Use Orchard Users and OpenID Server at the Default shell, with a fixed platform connection. Customer web shells are OIDC clients; API validation must reach the issuer's actual token/authorization store or use proven introspection. Same process does not mean same store. Shared authentication cookies across shells and per-tenant passwords are rejected. A separate identity service is deferred unless the PoC requires revisiting this ADR.

GlobalUserId is an immutable platform UUID. External identities map by exact issuer + subject, never by email. TenantId is an immutable platform UUID; ShellName and UrlPrefix are routing attributes, not identity. Membership is platform-owned and unique by GlobalUserId + TenantId. Tenant local profiles are optional subject links, never a second password source. ACL and user-role assignments belong to the customer DB in later authorization work.

AccountSecurityGeneration, TenantSecurityGeneration and MembershipGeneration are monotonic platform counters. Sessions and grant families have independent random IDs, their own revocation state, and capture all three generations at issuance. Remove/re-add creates a new membership generation. Unlock/reopen/renew cannot revive a revoked session or an expired issuance-time validity bound. Natural subscription expiry bounds credential/session validity at issuance; later extension does not extend existing credentials. `PlatformDbContext` owns the `identity` schema/migration; Orchard retains ownership of native Users/OpenIddict tables.

Use Authorization Code + PKCE, explicit JWT configuration, validated issuer/signature/audience/expiry/scopes and a server-validated tenant claim. A grant family is bound to one TenantId. The routed shell's TenantId must match; the token never selects a database. Web cookies are Secure/HttpOnly, independently named/scoped per shell, with anti-CSRF for mutations. Callback/logout destinations use a strict prefixed allowlist. The production boundary compares the independent platform client registry before native protocol handlers may redirect. No global mutable CurrentTenant or refresh token in localStorage.

Implemented lifetime proposals: access token 5 minutes, cryptographic clock tolerance 30 seconds; refresh idle 7 days and absolute 30 days; tenant and issuer web sessions idle 30 minutes and absolute 8 hours. Tenant limits are additionally bounded by subscription expiry captured at issuance. Sliding renewal cannot exceed the absolute bound. Server-side validation is required on each authorization; cookie expiration is not the revocation mechanism. The fresh native access-entry check also rejects an actually expired entry; the cryptographic tolerance does not extend the authoritative native expiry. Normal access-token expiry does not itself shorten the independently validated web session.

Signing/encryption/Data Protection keys are persisted outside Git with access control. Data Protection keys are encrypted with the deployment encryption certificate and isolated by shell purposes. Key reload after restart is covered; unattended overlapping rotation is not implemented. Existing-client secret changes and key rollover require explicit operational reconciliation, not startup auto-repair. See `docs/runbooks/m2-identity.md` for deployment boundaries and incident handling.

Refresh rotation is serialized by grant family, consumes a token once, and has no reuse grace window. Reuse revokes that family and its related tenant session, not independent families or other tenants. Concurrent refresh or a lost response can require re-login; clients single-flight refresh. Logout-tenant and logout-global have distinct server-side scopes. OAuth errors follow OAuth (`invalid_grant`), not business API 403 semantics.

## M2 implementation choices

The Default profile uses native Orchard Users and OpenIddict/YesSql for password verification, signing, code redemption and token/authorization storage. A deployment-owned `IOpenIdServerService` supplies trusted server settings and persisted certificates. Native document management and entity ID generation are explicitly composed rather than approximated by mock services. Customer shells use the ASP.NET Core OIDC code/PKCE handler; the only fixture substitution is HTTP transport.

API verification first checks the signed JWT and routed audience/tenant, then reads the platform account/membership/family state and actual Default token/authorization records. Web cookies similarly revalidate persistent sessions and Default authority at each request. Native entity caching is disabled for security authority. Required-source errors fail closed without cached Allow. Native access-entry revocation reaches web even when web is the first request after the commit, without invalidating independent grants.

Orchard 3.0.1's native failed-attempt increment returns the pre-increment count. The integration enforces the configured threshold using the native persisted count and changes the native security stamp on lockout. It does not introduce another password store. Unlocking alone cannot restore prior credentials. The minimal login form fails closed for accounts requiring a second factor; it does not bypass two-factor authentication.

Private maintenance owns identity initialization, explicit client registration, enrollment, membership/account/subscription mutations and operational audit. A completed initialization retry is verify-only. The opt-in production host uses registry-backed settings, restricted SQL credentials, fresh readiness and an explicit endpoint allowlist. HTTP startup never migrates or repairs state. Full authorization UI/roles/business entitlements remain M3 scope.

## Gate, consequences and evidence

The required initial native HTTP PoC passed before dependent production composition was added: branch `4c07a4e711c2460ded750938c47881a95405b9ae`, tested PR merge `0dd8c024d42c018251125b57db9f41a1403f2612`, run `42289975570`, 37/37 M2 cases with zero failed/skipped, plus all M0/M1 gates. This proves Default/Alpha/Beta SSO, prefixed independent cookies, exact subject mapping, cryptographic JWT checks, native-store revocation, refresh concurrency/reuse/lost-response behavior and source-failure handling on the pinned graph.

Production-composition and private-command contracts were then added test-first. The current full source-bound result, artifact digest, negative-case history and exact reproduction commands are in `docs/verification/m2.md`; the original nine-store-case-only handoff is archived separately in `docs/verification/m2-initial-store-poc.md`. A green store subtest or M0 build never substitutes for HTTP/production evidence. Missing mandatory cases, skip, zero execution, failure or cleanup error keeps the complete gate red.

Owner acceptance of the topology, lifetime defaults, strict lost-response/re-login policy, deployment/key-management constraints and final PR review remains outstanding. No independent security approval or production rollout is inferred from these implementation results, and this ADR is not Accepted.
